# Musicbot disaster recovery

Use the generic backup-plan module `musicbot_full` for a complete, administrator-managed Musicbot recovery. Its resource identifier is the existing Musicbot instance ID. The existing module `musicbot` and JSON download endpoints continue to export customer configuration. JSON option `type=full` includes the track catalogue; that JSON does not contain audio files and is not a disaster-recovery archive.

A `musicbot_full` archive contains exactly `full.json` and `assets.tar.gz`. The metadata is authenticated and encrypted using `SecretsCrypto` and the installation's `APP_SECRET` (or configured fallback secrets). Keep that secret securely with disaster-recovery documentation: recovery on an installation without a matching secret fails before any live changes. Connection ciphertext is preserved byte for byte, so the original secret keys are also needed to decrypt existing credentials.

The full export covers the instance's track catalogue and files, queue, playlists and items, radio stations/history/favourites, all plugin configuration and logs, AutoDJ settings and references, connections and encrypted credentials, schedules, workflows and executions, roles and assignments, stream settings, runtime event history and customer limits. The instance configuration includes its actual YouTube history. The export uses all database columns in these explicit tables; no 500-log truncation applies. Table schemas must match at recovery time. Encrypted metadata is bounded to 64 MiB of plaintext; oversized metadata fails instead of silently truncating history. Media bytes are streamed separately. Global, customer-shared media outside the managed instance directory and cross-instance references are rejected with an actionable failure rather than silently dropped. Move those resources into the instance scope before using full backup.

The agent must have the Musicbot installation root configured in `EASYWI_MODULE_BACKUP_ROOTS`. Its authenticated module archive API must be deployed together with the backend. The instance's configured systemd service is quiesced for filesystem replacement and its prior running/stopped state is respected by the agent. The archive is bound to the exact instance, customer, node, directory and service. Rebinding or migrating another instance is deliberately a separate administration operation; changing these fields in an archive cannot bypass authentication.

Transient directories `runtime`, `tmp`, `logs` and `run`, control sockets and PID files are excluded from the file archive. Socket/PID paths, runtime control/API tokens, the runtime payload and the database's instantaneous process status are not restored from metadata. Existing operational settings remain in place and the managed service creates new runtime state. Persisted event and plugin history are included; filesystem runtime logs are not.

Restore first validates authenticated metadata, schema, ownership, all relational references, the complete asset archive checksum and every local track's content checksum. Agent dry-run validates/extracts into private staging without changing the live filesystem. An apply creates a recovery snapshot of current files, restores metadata inside a database transaction and waits for the actual agent file operation. A failure rolls back the database and restores the prior files, including when a response was interrupted after apply. If remote rollback fails, the result is failure and identifies the retained private recovery archive for manual recovery; it is never reported as a completed restore.

Use the generic backup restore's dry-run first, then apply the same archive. Full recovery is administrator-controlled because it restores customer limits and role grants. Customer configuration imports retain masked-credential behavior and cannot consume a full encrypted archive.
